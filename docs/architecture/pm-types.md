# `pm-types`

`pm-types` is the vocabulary every other Rust crate shares: fixed-point prices and quantities, exchange timestamps, typed venue enums, the normalized input events the core consumes, and the commands it emits. It has no I/O and a single dependency (`serde`; `serde_json` only for tests). Every other crate depends on it; it depends on none of them. See [the repository overview](architecture.md) for where it sits.

## Modules

| Module | Contents |
| --- | --- |
| [`num`](../../crates/pm-types/src/num.rs) | `Px` and `Qty`, integer units of 10⁻⁴; `parse_fixed`; rounding and tick helpers |
| [`time`](../../crates/pm-types/src/time.rs) | RFC 3339 ↔ integer Unix nanoseconds, without a date library |
| [`venue`](../../crates/pm-types/src/venue.rs) | Wire enums (`Side`, `Intent`, `OrderState`, `ExecKind`, `MarketState`), `RejectClass`, `Feed`, `Tif` |
| [`event`](../../crates/pm-types/src/event.rs) | Input frames, the `Event` enum, REST results, the `Command` enum, and drain/dispatch priorities |

The crate root re-exports `event::*`, `venue::*`, and the main `num` items, so callers write `pm_types::Px` or `pm_types::Event`. `time` is used by path (`pm_types::time::parse_rfc3339_ns`).

## Numbers

`Px` and `Qty` are both newtypes over `i64` in units of 10⁻⁴ (`SCALE = 10_000`), generated by one macro so they share arithmetic, formatting, and serde behavior but cannot be mixed by accident.

- **Parsing is textual.** `parse_fixed` reads the decimal string directly: `"0.01"` is exactly 100 units with no float round trip. Digits beyond the fourth decimal place are accepted only when they are zeros; anything else is an error rather than a silent rounding.
- **Serde reads strings and JSON numbers exactly.** Values serialize as strings such as `"0.5550"`. Strings and JSON numbers deserialize through `parse_fixed`: with `serde_json`'s `arbitrary_precision` (enabled in this workspace) a number arrives as its text, so `0.42` and `"0.42"` decode alike, and a fifth non-zero decimal is an error in both. Floats from formats without exact text (TOML, `f64`) go through their shortest round-tripping text, so `0.1` is exact and `0.1 + 0.2` is rejected rather than rounded. Out-of-range integers are an error. The whole stored range, including `i64::MIN`, round-trips through text.
- **Arithmetic saturates.** `+`, `-`, negation and `complement` stop at the `i64` bounds instead of panicking (debug) or wrapping (release). Real prices and sizes are many orders of magnitude inside them; a core benchmark showed no measurable cost.
- **Float conversion.** `from_f64` rounds and is for values known to be finite (model output, validated config); `try_from_f64` returns `None` for NaN, infinities and out-of-range values. `Config::validate` rejects `nan`/`inf` anywhere in the config.
- **Price helpers** cover the YES-price convention: `Px::MIN`/`Px::MAX` (0.01–0.99), `complement()` for the NO-side view (1 − p), `is_on_tick`, `floor_to`/`ceil_to` for outward rounding (a non-positive tick leaves the price unchanged, as `Qty::round_down` does), and `clamp_to`.
- **Quantity helpers** include `round_down(min_qty)` (the venue silently truncates off-increment sizes, so the core does it explicitly) and `notional(px)` for dollar values.

Floating point is used elsewhere for model values, cash, and reporting; executable prices and sizes always pass back through these types.

## Time

Exchange stamps carry up to nine fractional digits, so they are stored as `i64` Unix nanoseconds. `parse_rfc3339_ns` handles `Z`, numeric offsets, and a space instead of `T` (the Parquet export format); civil-date conversion uses Howard Hinnant's algorithm. The parser never panics: non-ASCII input, impossible dates (including leap years), clock values out of range, offsets other than `±HH[:MM]` (so `+0200` is rejected rather than read as 200 hours), and times outside the `i64` nanosecond range (after 2262) all return `None`. Two formatters exist for the two consumers: `format_rfc3339_secs` for `goodTillTime` (whole seconds, as the venue expects) and `format_rfc3339_micros` for journals. `NS_PER_SEC` and `NS_PER_MS` are the shared constants.

## Venue enums

The `wire_enum!` macro defines each venue enum with a `from_wire`/`wire` pair and an extra `Unknown` variant. A new enum value from the venue therefore decodes as `Unknown` instead of failing the frame. Helpers encode the YES-book conventions:

- `Side::sign()` is +1 for a YES buy and −1 for a YES sell; `opposite()` flips it.
- `Intent::side()` maps the four intents onto the YES book: `BuyLong`/`SellShort` are bids, `SellLong`/`BuyShort` are asks.
- `OrderState::is_terminal()` defines which venue states end an order's life: `Filled`, `Canceled`, `Rejected`, `Expired`. `Replaced` is not terminal: a modify keeps the order ID, and the venue reports the still-working order as `REPLACED` on the socket and over REST until it fills or is cancelled (confirmed live on 2026-10-28).

`RejectClass` is the core's classification of failures (`BookMoved`, `Transient`, `RateLimited`, `Funding`, `MarketUnavailable`, `OurBug`, `Fatal`, `Unknown`); `pm-venue` assigns it and the core reacts to it. `Tif` has a single variant, `Gtd(ns)`. Making it impossible to express GTC, DAY, or IOC at the type level enforces the bot's "make markets only, always with an expiry" rule.

## Events in

[`Event`](../../crates/pm-types/src/event.rs) is the only input the core accepts. Feeds, the gateway, the admin socket, the web UI, and the backtest simulator all produce it.

| Group | Variants | Produced by |
| --- | --- | --- |
| Control | `Markets`, `Connection`, `Admin` | Discovery, feed tasks, admin socket and UI |
| Order and account feedback | `OrderSnapshot`, `Execution`, `Position`, `Positions`, `Balance`, `RestResult`, `OpenOrders`, `OrderLookup` | Private stream and REST results |
| Game | `Game`, `GamePolled` | Game poller |
| Market data | `Trade`, `Book` | Market stream |

`Event::priority()` returns 0–4 in that order; the core sorts each tick's batch stably by it, and the live inbox drains in the same order.

The frame types carry what the core needs and nothing venue-shaped:

- `MarketParams`: one tradable market from discovery, including tick, minimum quantity, fee coefficient, scheduled start, team names, and which team (`TeamOrdering`) is YES.
- `BookFrame`: a full L2 replacement, best level first. `problems(tick)` lists ordering, crossing, quantity, range, and off-tick defects before the core accepts it.
- `TradeFrame`: a public fill; `taker_side` is the only reliable direction.
- `GameFrame`: score as legs `(home, away)`, period, live and ended flags; `cancelled()` recognizes the `CAN` period.
- `VenueOrder`, `ExecutionFrame`, `FillInfo`, `Reject`: private execution reports.
- `RestResult`: a `RestKind`, the request's `Token`s, and a `RestOutcome` (`Accepted`, `Withdrawn`, `GatewayRejected`, `RateLimited`, `AuthFailed`, `Ambiguous`). `Accepted` for modify and cancel is only an echo; lifecycle truth comes from executions.

`Slug` and `OrderId` are `Arc<str>` so they can be cloned across maps and queues cheaply.

## Commands out

[`Command`](../../crates/pm-types/src/event.rs) is everything the core can ask the shell to do: `Place`, `Modify`, `Cancel`, `CancelAll`, `Withdraw` (drop a queued, unsent action), the reconciliation reads (`QueryOpenOrders`, `QueryOrder`, `QueryPositions`, `QueryBalance`), and `RefreshMarket` (re-run discovery). Every order action carries a `Token`, the core's own monotonic request ID; it is journaled but never sent to the venue, because the venue has no client-order-ID field.

`Priority` orders the gateway queue: `CancelAll < Cancel < Reduce < Quote < Refresh < Read`. Order actions carry an explicit priority chosen by the core; `Command::priority()` fills in the rest (`Withdraw` ranks with cancel-all so it overtakes what it withdraws).

## Design notes

- The crate is deliberately behavior-light. Validation that depends on market state (staleness, orientation, risk) lives in `pm-core`; only shape checks that need no state, like `BookFrame::problems`, live here.
- All types are `Serialize`/`Deserialize`, so the live journal can record events and commands verbatim and replay them through the core.
- Changing a type here touches every crate. Wire-format changes should normally stop in `pm-venue`'s decoders rather than reach these types.
